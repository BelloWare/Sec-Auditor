# Security questions, query coverage, and evidence limits

This matrix starts from the security question an agent must answer. It distinguishes data the MCP can collect, evidence that depends on an already-running service, and questions that remain unresolved. A broad resource list is useful discovery, but it is not a complete security assessment. An IAM role is permission to ask a question; it is not proof that a scanner, log sink, cluster route, or historical dataset exists.

For the exact GCP endpoint/parameter/permission catalog, see [gcp-coverage.md](gcp-coverage.md). Alibaba has its own implemented API/action catalog, identity requirements and limitations in [alicloud-coverage.md](alicloud-coverage.md). Use the running server's `capabilities` and `list_security_checks` before planning an assessment. A query kind can supply useful evidence without having a dedicated built-in deterministic check.

## Evidence labels

| Label | What it means | What it does not establish |
| --- | --- | --- |
| Live configuration | A native read of current control-plane configuration. | Guest/container runtime state, complete effective access, historical behavior, or the absence of omitted/denied resources. |
| Inventory | Indexed resource/IAM metadata or a provider inventory snapshot. | Immediate freshness or exhaustive asset coverage. |
| Existing report | A vulnerability/finding/inventory record already generated by an enabled service. | That the target was recently or fully scanned. An absent record is unknown coverage. |
| Bounded events | Entries visible to an authorized, bounded log query. | Events outside retention/window/sampling, disabled log classes, or entries in other storage/view scopes. |
| Unimplemented / separate sensor | This implementation cannot collect enough evidence for the question. | A passing result. It must remain unknown, unsupported, or explicitly out of scope. |

Every native page token, partial failure, denied permission, inaccessible location, sampling setting and observation timestamp matters. An agent must retain those qualifications in its findings. Never convert a collection failure or lack of evidence into a passing security control.

## GCP question matrix

The `gcp.` prefix below identifies the provider query kind used through `collect_resources`. Methods named `list` or `get` mean the query's `operation`; they are not free-form API methods. `project` and canonical `scope` are mutually exclusive.

| Security question | Implemented evidence / how to query | Evidence class and important remaining limits |
| --- | --- | --- |
| Which organizations, folders, projects, and resources are in scope? | `gcp.resourcemanager.organization`/`folder`/`project` get; `gcp.resourcemanager.folders` and `projects` list under an authorized parent; `search_inventory` for allowed CAI types; native project lists. | Hierarchy metadata is live; CAI is inventory. Hierarchy list returns direct children: traverse folders and all pages explicitly. The allowlist excludes data objects and secret resources. Inventory is not a promise of native support for every GCP product. |
| Who is granted roles on projects, folders, organizations, buckets and service accounts? | `get_iam_context` direct policy with optional ancestor reads; `search_inventory` IAM mode; `gcp.iam.policy` get; `gcp.storage.bucketIamPolicy` get; `gcp.iam.serviceAccountIamPolicy` get. | Direct allow-policy reads request version 3. CAI policy search is indexed and may return only matching bindings. A service-account resource policy describes grants **on** the account; search other policies for grants **to** it. |
| What permissions do those roles contain? | `gcp.iam.predefinedRoles` list/get; `gcp.iam.roles` list/get at project or organization scope, FULL role definitions for lists. | Live definitions, including included permissions. Preserve disabled/deleted stage and scope semantics. Reading a role does not calculate resource- or condition-specific effective access. |
| Are deny policies or principal access boundaries restricting access? | `gcp.iam.denyPolicies` list then get each policy; `gcp.iam.principalAccessBoundaryPolicies` at organization scope; `gcp.iam.policyBindings` at project/folder/org scope. | Live attached definitions/bindings. Deny list omits rules. Inspect ancestors, relevant bindings and conditions. Group expansion, directory membership and a full IAM policy evaluator/simulator are not implemented. |
| Can external workloads or identities impersonate a service account? | Service-account allow policy; `gcp.iam.workloadIdentityPools` list; `gcp.iam.workloadIdentityProviders` list/get with a confined numeric-project pool parent; indexed IAM grants and role definitions. | Trust, issuer, audience, attribute mapping/condition and impersonation grants are configuration evidence. No token generation, impersonation attempt, or external identity-provider verification is performed. |
| Are long-lived service-account keys exposed, old, disabled or expiring? | `gcp.iam.serviceAccounts`; project-wide `gcp.iam.serviceAccountKeys`; per-account `gcp.iam.serviceAccountKeyMetadata`; bounded audit-log evidence for observed use. | Key metadata only; no key bytes. Creation/expiry/disabled state is available. Key metadata is **not** an authoritative last-used record; silence in retained logs does not prove never used. Full key-usage telemetry and IAM recommender history are not implemented. |
| Which organization constraints actually apply to a project/folder? | `gcp.orgpolicy.policies` list/get; `constraints`; organization `customConstraints`; `gcp.orgpolicy.effectivePolicies` get by constraint ID. | Live direct and effective policy evidence are separate. Effective API merges hierarchy/evaluates conditions and does not expand `under:` subtrees. Inspect provider response and policy provenance; a missing direct project policy is not no enforcement. |
| Are VM configurations hardened? | `gcp.compute.instances`, `project`, templates, disks, images, snapshots and instance group configuration; exact gets for the resource's real zone/region/global scope. | Control-plane settings: service account/scopes, Shielded VM/secure boot, metadata flags, network exposure, encryption and provisioning. Arbitrary metadata values and startup commands are projected out. No guest execution, mounted disk content, serial console or screenshot access. |
| Are VM operating systems patched or vulnerable? | `gcp.osconfig.inventories` with FULL list view and `gcp.osconfig.vulnerabilityReports` for an explicit zone; SCC findings. | Existing VM Manager/SCC reports only. Sensor enrollment, last update, supported OS, package coverage and scanner availability determine confidence. No fresh scan, malware hunt, process enumeration or guest hardening assessment. |
| Are VPC networks, subnets, routes, NAT, peering, VPN and Private Service Connect configured safely? | Compute networks/subnetworks/routers/routes/addresses/VPN gateways+tunnels/service attachments and exact configuration gets. | Live control-plane topology. Not every hybrid-network product or route status API is implemented; for example Interconnect detail collectors are absent. No active packet probe or generalized reachability simulation. |
| Which firewall rules actually apply to a VM NIC? | VPC `gcp.compute.firewalls`; `gcp.compute.hierarchicalFirewallPolicies`; global and regional network firewall-policy lists/gets; `gcp.compute.effectiveFirewalls` get with zone, VM ID and `network_interface` (default `nic0`). | The effective-firewall API supplies applicable NIC rules. Policy priority/associations, disabled rules, routing, target selectors and other hops still need interpretation. It is not proof a specific connection succeeds or fails end to end. |
| Are load balancers and application edges exposed or weakly configured? | Forwarding rules, target HTTP/HTTPS proxies, URL maps, backend services/buckets, health checks, SSL policies, global/regional Cloud Armor security policies; exact gets. | Live service/edge configuration. Full certificate lifecycle and private key material, all TCP/SSL proxy families, WAF efficacy and application-layer exploit testing are not implemented. Treat unsupported dependencies as missing coverage. |
| Do VPC Service Controls perimeters cover sensitive resources and access paths? | Organization `gcp.accesscontextmanager.accessPolicies`; `servicePerimeters` and `accessLevels` list/get under an ownership-verified access policy. | Live enforced `status` versus dry-run `spec`, ingress/egress policy and access-level definitions. This is not a policy simulator or exfiltration test. Access policy ownership is proved before globally addressed nested reads. |
| Are flow logs enabled, sampled and routed, and what traffic was observed? | Compute subnet `logConfig`; project/org `gcp.networkmanagement.vpcFlowLogsConfigs`; applicable `orgVpcFlowLogsConfigs`; Logging sinks/buckets/views/exclusions; dedicated `query_logs` VPC-flow mode. | Live config plus bounded existing events. No log generation/enablement; interval, sampling, metadata selection, routing, retention and location determine coverage. Missing entries never prove no traffic. |
| Are audit logs enabled, retained, encrypted, excluded or exported? | IAM audit configs from direct IAM policies; Logging sinks/exclusions/buckets/views/metrics/settings/CMEK settings; `gcp.monitoring.alertPolicies`; bounded `query_logs`. | Settings and bounded entries are distinct evidence. A sink existence check does not establish destination write success or downstream retention. Data Access availability and log-view permissions must be verified. Notification credentials are not collected. |
| Are GKE clusters and node pools configured securely? | `gcp.container.clusters` list/get and nested `gcp.container.nodePools` list/get, including control-plane exposure, release/version, network and workload identity configuration. | Live GKE settings. The service still needs reachable Kubernetes control-plane endpoints and suitable Kubernetes authorization for object-level inspection. IAM role assignment does not create network reachability. |
| Can the agent inspect pod definitions without Kubernetes Secret content? | `inspect_kubernetes` on the explicit built-in allowlist: pods, controllers, service accounts, roles/bindings, network policy, admission policy and other listed kinds. Definitions are projected before output. | Spec/RBAC/network/admission evidence. Secrets, ConfigMaps, pod logs, exec/attach, port forwarding, token requests and arbitrary CRDs are excluded. Inline env values, commands and sensitive annotations are redacted. Narrow RBAC is not a subtraction from broader GKE IAM authorization. |
| Are workloads privileged, unconfined, over-permissioned or poorly isolated? | Kubernetes pod/controller security contexts, host namespaces/volumes, capabilities, service-account token behavior, RBAC, network policy and admission configuration; built-in checks from `list_security_checks`. | Definition-level risk. Existing definitions do not prove runtime enforcement, image provenance, loaded kernel modules or absence of privilege escalation. Pod names/images/references may be visible; Secret values are not read. |
| Are container images vulnerable and is deployment admission restricted? | `gcp.artifactregistry.repositories` settings; fixed `gcp.artifactanalysis.vulnerabilities` occurrence query; `gcp.binaryauthorization.policy` and GKE binary-authorization setting; SCC. | Existing vulnerability reports and admission configuration. Occurrence filter is fixed to VULNERABILITY and other kinds are discarded. No registry/image bytes, build/source downloads, fresh scan, signature generation, attestor-key retrieval, or runtime filesystem inspection. |
| Are buckets public, encrypted, retained and governed safely without object reads? | `gcp.storage.buckets` list/get (`projection=full` for get); `gcp.storage.bucketIamPolicy` get; CAI IAM search. Bucket membership is proven via authorized project list before global bucket requests. | Bucket metadata, default ACL/bucket ACL where available, public-access-prevention, uniform access, encryption/lifecycle/retention/versioning, IAM. No object listing, object ACL enumeration, download, content scan or signed URL creation. Optional IP-filter field needs its additional read permission. |
| Are managed database configurations exposed or weakly encrypted? | `gcp.sql.instances` list/get; `gcp.bigquery.datasets` list/get with dataset detail enrichment; IAM-policy search and org policy. | Database instance/dataset configuration only. No SQL query/rows, database user grants/passwords, table data, query history or extraction. BigQuery table/column policy and all other managed database products are not natively covered. |
| Are serverless service definitions and identities secure? | Cloud Run services/jobs and Cloud Functions list/get in explicit supported locations; IAM-policy search for resource bindings; existing logs. | Resource definition, network exposure, service identity, encryption and build/runtime references. Inline values/commands/source fields are projected. No invocation, source archive retrieval, job execution or application security testing. |
| Are encryption keys and secret resources governed appropriately? | KMS rings, inventory/live keys, version metadata; Secret Manager secret metadata; direct/IAM-search grants where supported; org policies. | Rotation/state/protection level/replication/labels and references. No decrypt/sign/encrypt, public/private key export, key attestation bytes or Secret Manager version payload. Not an assurance that every stored data byte is encrypted with the expected key. |
| Are messaging, DNS and enabled-service surfaces appropriate? | Pub/Sub topic/subscription configuration, DNS managed zones, enabled service list, monitored alert policies. | Control-plane metadata. No Pub/Sub payload/pull, DNS record-set detail collector, arbitrary custom metric data, notification credentials or message delivery validation. |
| What has the security platform already found? | SCC sources and findings at authorized project/folder/org and explicit data location; Artifact Analysis and OS Config reports; `get_evidence` and assessment results. | Existing-report coverage. Unsupported data source, disabled service, permission denial, absent/old scan, exhausted budget or omitted page stays unknown/partial. No security product is enabled or configured by the MCP. |

## A complete query plan is explicit about its boundary

1. Establish the caller's allowed provider roots, projects/accounts, regions/locations, and registered Kubernetes connections. Read `capabilities`; plan only advertised operations. Discover direct child projects/folders and all pages when organization coverage is intended.
2. Collect inventory and live control-plane settings by security family. Run bounded bulk queries in parallel when independent; keep dependencies sequential (discover a KMS key before listing versions, discover an organization access policy before reading its perimeters).
3. Retrieve exact details and policies needed to answer each question: role definitions, ancestor/direct IAM, deny rules and PAB bindings, effective org policy, effective NIC firewalls, nested log views and live KMS metadata. Preserve both the root scope and specific resource name in evidence.
4. Query already-existing security reports and bounded event windows. Record scanner/log prerequisites, report times, retention/sampling, explicit region/location selection, and every denial or missing page.
5. Run registered deterministic checks and reason over the projected evidence. Report a control as passed only if its required evidence is complete enough. A new query family does not imply a matching built-in check exists.
6. Produce findings with evidence IDs, observed time, affected provider/root/resource, confidence, and missing evidence. A full result says which portions were assessed and which remain unknown; it does not infer runtime security from a large item count.

Bulk collection and assessment jobs are read-only observation mechanisms. They have limits on concurrency, response size, pages, items and duration. A batch containing independent successful and denied queries should retain both outcomes, rather than abandoning the success or suppressing the denial. Provider-specific scope enforcement continues to apply to every item in the batch.

## Cross-provider contract and Alibaba boundary

GCP and Alibaba share evidence/result/error, pagination, projection, assessment and caller-authorization concepts. They do not share IAM vocabularies, resource names, credential chains, regions or implicit administrative scope. An Alibaba RAM role cannot be interpreted as a GCP organization IAM role, and a GCP organization permission does not authorize an Alibaba account.

Alibaba queries use `provider=alicloud` and an explicitly permitted `account_id`, plus the required region and resource selectors. Alibaba ActionTrail/log query availability and registered ACK/Kubernetes access have their own capability declarations. The authoritative implemented Alibaba list/get actions, supported services and missing actions are documented in [alicloud-coverage.md](alicloud-coverage.md); do not infer provider parity from the GCP matrix above. Registered SLS aliases and Kubernetes connections are operator configuration, not arbitrary agent-selected endpoints.

## Verification and sources

The endpoint, parameter, pagination, ownership proof and content-exclusion cases are exercised with local/mock tests. These tests establish request construction and service behavior; they do not establish that any particular customer account grants the needed permissions or has valid telemetry. Before production use, run a bounded acceptance assessment in known test scopes and inspect the resulting denials, unknowns and timestamps.

Primary API sources and semantics for the GCP matrix are linked in [gcp-coverage.md](gcp-coverage.md), including effective-firewall rules, direct/effective organization policies, IAM deny/PAB APIs, bucket projection, scoped SCC, Artifact Analysis occurrence kinds, VPC-SC ownership and flow-log configurations. Kubernetes-specific restrictions are in [kubernetes.md](kubernetes.md), and identity/IAM setup is in the repository's deployment documentation. Keep those source-backed boundaries when presenting results to an AI agent.
